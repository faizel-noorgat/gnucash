**Decisions passed:**

- 2026-09-19 — **(Implementation) The two database connections are two aliases against one database, differing only in credential.** `default` is the runtime role, `deploy` is the owning role, and `split_databases()` derives both from one connection dict so engine, name, host, port and options cannot drift apart. `manage.py migrate --database=deploy` is the only thing that uses the owning role. Reasoning: RLS is only worth the role that connects to it, and a single shared `DATABASES['default']` was the structural reason the split had not been made.
- 2026-09-19 — **(User directive) The `deploy` alias keeps the existing privileged role; no new role is created for it.** A `BYPASSRLS` role was rejected outright (standing rule). A *non-superuser* owning role was rejected on evidence: **FORCE ROW LEVEL SECURITY binds the table owner too**, so a role the policies apply to cannot run the cross-tenant `tenant_id` backfills and would **update zero rows in silence** rather than fail. The owning role therefore has to be able to bypass, and the security property being bought is that the *runtime* never does.
- 2026-09-19 — **(User directive) Development runs the split too, which requires `RLS_ENABLED = True` there.** With `default` as `app_user` and context propagation off, the middleware issues no `SET LOCAL` and every tenant-scoped query returns zero rows — a failure that reads as missing data rather than a switched-off boundary. Development is where a missing or wrong tenant context should surface, not production.
- 2026-09-19 — **`config/settings/test.py` keeps a single privileged alias, and cannot do otherwise.** Django's test runner creates *and* migrates the test database through the `default` connection, so the role that migrates is the role the tests then run as; `test_db_signature()` also excludes USER, so a second alias with different credentials collapses into the same test database as a mirror. `SET LOCAL ROLE app_user` inside `rls_session()`/`app_role()` is equivalent within the block, and that is what the isolation assertions rest on. The inverse is the cost, now recorded as F-0010: a test that does not enter one of those runs as a superuser and cannot detect a missing tenant context.
- 2026-09-19 — **`NOLOGIN` is removed from `common/rls/migrations/0001`'s re-asserting `ALTER ROLE`.** Roles are cluster-scoped while databases are not, so that statement ran once per database and revoked the runtime credential **cluster-wide** on every freshly migrated database — and `pytest` creates one per run. Reproduced, not theorised: grant LOGIN, run `pytest tests/rls/test_rls_provisioning.py`, `rolcanlogin` is back to false. This means **editing an already-applied migration**, accepted deliberately: it never re-runs on an existing database, so no schema or policy diverges; the four attributes that make the role safe to connect as are still re-asserted on every database; and `LOGIN` is not a bypass — a connected `app_user` is still `NOSUPERUSER`, `NOBYPASSRLS`, owns nothing, and is bound by all 57 policies.
- 2026-09-19 — **`rls.W001` inspects only the `default` alias, and stays a warning.** It carries `Tags.database` but is deliberately not per-alias: `deploy` is *expected* to bypass, so iterating every alias would report the correct configuration as a fault, which is how a check gets switched off. Severity stays a warning because `manage.py migrate` runs system checks and a deployment with one privileged alias must be able to reach the split before it can be told it is wrong. The message now names the alias it inspected and the `--database=deploy` route it left alone.

Older decisions (RLS closure, posting atomicity, tenancy centralisation, ADR-010 immutability, modernization target) are unchanged and remain in the entries below:

- 2026-09-19 — **(User directive) Practice and PracticeMembership visibility must be scoped; being global platform entities does not make them acceptably enumerable.** Previously recorded as the stated residual of the B-0005 closure on the grounds that a Practice has no tenant to key a policy on. The user has rejected that as a resting state: absence of a tenant is a modelling reason to use a different key, not a reason to leave access-control data readable by every runtime connection (F-0009).
- 2026-09-19 — **A child's tenancy is materialised or derived, chosen by domain ownership, not applied uniformly.** Five children that carry business/financial payload and are queried directly — `accounting_journalline`, `business_documents_document_line`, `_document_attachment`, `document_extractions`, `document_matches` — get their own `tenant_id` and a plain equality policy. Nine where duplicating it would make the model worse — `role_permissions`, `advisor_access_grants`, `workflow_transitions`, `reporting_dashboardwidget`, `accounting_transactionmetadata`, `_counterpartposting`, `_reconciliationauditlog`, `business_documents_approval_step`, `document_extraction_versions` — get an `EXISTS` policy against their authoritative parent. An `EXISTS` subquery is itself RLS-filtered, so entity narrowing propagates to indirect children for free; only direct-equality children need the entity clause spelled out.
- 2026-09-19 — **Consistency between a child and its parent is a composite foreign key, not a trigger.** `FOREIGN KEY (parent_id, tenant_id) REFERENCES parent (guid, tenant_id)`, requiring a `UNIQUE (guid, tenant_id)` on the parent (free — `guid` is already the PK). A trigger could additionally *fill the column in*, and was rejected: a trigger that silently rewrites a caller-supplied `tenant_id` converts an application bug into a successful write with different data. The key rejects the write instead, at the point of the mistake, and holds against raw SQL the ORM never saw. `ON DELETE CASCADE` mirrors the models' `on_delete`. `TenantDerivedChildModel.derive_tenant_id()` handles the ORM side so ordinary callers never choose a tenant.
- 2026-09-19 — **A child's tenant column mirrors the *shape* of its parent's, not a stricter one.** `JournalLine`, `DocumentLine` and `DocumentAttachment` take a real FK to `Tenant` because their parents do; `DocumentExtraction` and `DocumentMatch` take a bare `UUIDField` because `Document.tenant_id` is a bare `UUIDField`. A child typed more strictly than its parent is not safer — it makes rows the parent accepts impossible to attach anything to. (Found by a passing test breaking: a FK from `document_extractions` to `tenants` rejected an extraction whose document was created against a fabricated UUID.)
- 2026-09-19 — **RLS policies are `TO app_user`, reversing the previous session's `TO PUBLIC` decision.** The earlier reasoning — that naming a role leaves the policy inapplicable to others, and default-deny is an outage rather than a leak — is still true and is still the wrong trade. `PUBLIC` makes the policy a statement about nobody in particular and silently extends it to every role ever granted privileges on the table. Least privilege and default deny mean naming the role. Implemented with `ALTER POLICY ... TO app_user` rather than DROP/CREATE, so the predicates written and reviewed in `0002` are not restated and cannot drift.
- 2026-09-19 — **The pre-context read set, and check-before-set ordering.** `AuthorizationService.can_access_tenant()` reads `memberships`, `advisor_access_grants`, `client_engagements` and `tenants` — the very tables RLS confines — so with no tenant context it returns `False` for everyone, including legitimate members. Four permissive `FOR SELECT` policies grant a caller their own rows: `memberships.user_id = get_current_user_id()`, `tenants` via a membership of theirs, `advisor_access_grants.practice_user_id = get_current_user_id()`, `client_engagements` via a practice membership of theirs. Permissive policies are OR'd, so these widen SELECT only; writes still require context. The middleware then follows the order the user asked for — authenticate → requested tenant → `can_access_tenant()` → establish context — and a middleware bug yields *no* context and zero rows, i.e. it fails closed. The advisor variant is deliberately **weaker** than the authorization rule (it ignores grant status, revocation and expiry): it answers "which tenants may you ask about", not "which may you use", and a second copy of the rule that drifts would lock out a legitimate advisor.
- 2026-09-19 — **`TenantContextMiddleware` owns a `transaction.atomic()` around `get_response`.** It cannot be a `MiddlewareMixin`: `process_request` runs before the view and in autocommit, so every `SET LOCAL` it issues is discarded — confirmed directly against PostgreSQL (`WARNING: SET LOCAL can only be used in transaction blocks`). The cost is real and accepted: every request holds a transaction open for its duration, and a `StreamingHttpResponse` outlives the block carrying the context. There is no way to have transaction-local RLS context without a transaction spanning the work that uses it. The authorization decision is **not** gated on `RLS_ENABLED` — that setting switches off the database mechanism, and using it to skip the check would make every non-RLS environment accept any tenant id from any authenticated caller.
- 2026-09-19 — **`tenants` is policed, keyed on its own primary key (`guid`).** SELECT is permitted for the current tenant or any tenant the caller holds a membership in; UPDATE/DELETE for the current tenant only; INSERT has a bootstrap carve-out requiring an authenticated user who records themselves as `created_by_id`, because registration creates a tenant before any membership can authorize reading it back. That carve-out is the whole bootstrap allowance and grants nothing but the ability to create the row.
- 2026-09-19 — **`roles` exempts system roles explicitly:** `tenant_id = get_current_tenant_id() OR (tenant_id IS NULL AND is_system_role)`. A bare equality would make every system role invisible and silently remove the permissions it grants, because `AuthorizationService.has_permission` explicitly matches `Q(tenant=tenant) | Q(tenant__isnull=True)`. The `is_system_role` half keeps an accidental NULL from becoming globally visible. `role_permissions` inherits the same rule through its `EXISTS`.
- 2026-09-19 — **`accounting/0004` disables the ADR-010 line trigger for its backfill, and re-enables it.** The trigger compares the whole row (`to_jsonb(OLD)` minus an allow-list), so the `UPDATE` setting `tenant_id` on lines of *posted* entries would raise `ADR-010: line ... is immutable`. The alternative — amending the trigger to permit a NULL → value transition on `tenant_id` — was rejected as leaving a permanent exception in an immutability guard for the benefit of a one-off migration. The migration is atomic, so a failure between the disable and the re-enable rolls both back; `test_the_posted_immutability_trigger_survived_the_tenant_backfill` asserts the trigger is enabled afterwards rather than trusting the comment.
- 2026-09-19 — **`rls.W001` warns, rather than errors, when the connection can bypass RLS.** Severity is a warning because migrations genuinely need the owning role and there is a single `DATABASES['default']`; an error would block `manage.py migrate` on exactly the deployments that need to run it.
- 2026-09-19 — **Creating a policy on a table whose RLS is not enabled is a silent no-op**, because PostgreSQL only consults policies once `relrowsecurity` is set. The first draft of `rls/0004` shipped exactly that on 14 tables, with every other assertion still passing. Every newly policed table now goes through `_enable_and_policy()`, and `test_a_policy_alone_does_not_count_as_isolation` asserts the `relforcerowsecurity` flag rather than the mere existence of a policy.
