**Decisions passed:**

- 2026-09-19 — **The posting rollback is proven by fault injection, not by construction.** The fault is raised by patching `AuditEvent.log`, the last step `post_document()` performs, passing every other audit write through so the engine's own `JOURNAL_POSTED` event does not abort the posting early. The test runs under `django_db(transaction=True)` so `post_document()`'s `atomic()` is a **real outermost transaction** (PostgreSQL BEGIN/ROLLBACK), not a savepoint inside a test-managed one — "nothing left committed" is only meaningful if a COMMIT was possible. It records the transaction's uncommitted state at the fault instant and asserts a *posted* journal and a *POSTED* document were both present, so the rollback assertions cannot pass vacuously. Falsification attempt: removing the outer `atomic` made both tests fail, but on `select_for_update cannot be used outside of a transaction` rather than on the absence assertions — recorded plainly rather than overclaimed. (T-0016, and the gap noted in the previous handoff.)
- 2026-09-19 — **Role permission resolution has exactly one definition.** `Role.get_permissions()` queries the `RolePermission` through-model (`related_name='role_permissions'`) rather than the never-declared `self.permissions`, and `AuthorizationService.has_permission` resolves through it instead of re-deriving the join. Two independent copies of one access-control rule is how the model method rotted into a reference to a relation that did not exist. (T-0016)
- 2026-09-19 — **RLS helper functions `RETURN uuid` and fail closed or loud.** Absent or empty context yields `NULL` → policies deny → no rows. Malformed context **raises** `invalid input syntax for type uuid`. The `EXCEPTION WHEN OTHERS THEN RETURN NULL` handler is **removed, not narrowed**: it made a bug in the context writer indistinguishable from a legitimately absent context. The functions are `DROP`ped before `CREATE` because `CREATE OR REPLACE` cannot change a return type and would have aborted on exactly the deployments that had run the old `docker/init-db.sql`. (B-0004)
- 2026-09-19 — **RLS policies are `FOR ALL TO PUBLIC`, with `ENABLE` and `FORCE`, on the 36 tables carrying a direct `tenant_id`.** Named at `app_user` a policy would leave any other role default-denied — an outage rather than a leak, but still wrong; the policy describes the table's security model, not one caller. `ENABLE` alone exempts the owner and an owner can always disable its own security, so `FORCE` closes that. Tables carrying `legal_entity_id` narrow further when entity context is set, and treat absent entity context as the whole tenant. (B-0003)
- 2026-09-19 — **RLS is the tenant boundary; `AuthorizationService.can_access_tenant()` decides which tenant a caller may assume.** The practice/engagement/grant chain is deliberately **not** duplicated into SQL policies: encoding one authorization rule twice is the failure mode that produced the `Role.get_permissions()` defect. `common/rls/tasks.py`'s `TenantScopedTask` and the HTTP middleware establish context; RLS confines whatever context is set. A test states this plainly rather than implying RLS gates the chain.
- 2026-09-19 — **`app_user` owns nothing and has no `BYPASSRLS`; the runtime must connect as it.** Ownership is itself a bypass — an owner can always `ALTER TABLE ... DISABLE ROW LEVEL SECURITY`. Related and important: **a superuser bypasses RLS even against a `FORCE`d table** (confirmed directly against PostgreSQL before being relied on). Django's test connection is the `postgres` superuser, which is why the RLS tests drive their assertions through `SET LOCAL ROLE app_user` and why enabling RLS did not break the existing suite.
- 2026-09-19 — **`docker/init-db.sql` no longer defines functions or policies** — it creates the role and nothing else. Two definitions of one security function, only one of which is executed, is how the wrong one survives. Migrations under `common/rls/` are the single definition; a clean deployment gets the correct policies from `manage.py migrate` whatever the database is called.
- 2026-09-19 — **`TenantScopedTask` was created, not verified.** The requirement asked that it be verified, but zero references to it existed anywhere in the tree. It runs the task body inside one `transaction.atomic` (not decoration: `SET LOCAL` is discarded at the end of the transaction it was issued in) and raises rather than silently reading zero rows when a tenant-scoped task is called without `tenant_id`.
- 2026-09-19 — `common/rls` became an installed app so the RLS schema changes have a home in the migration graph. Its `__init__.py` no longer re-exports the abstract models: Django imports an app package while populating the registry, so the eager import died with `AppRegistryNotReady`. Nothing outside the package imported them.
- 2026-09-19 — **Posting is one atomic domain operation.** `DocumentPostingService.post_document()` owns the complete lifecycle: lock → validate → post → mark posted → persist the journal reference → audit → commit once. The legacy two-step contract (`post_document()` then a caller-side `mark_posted()`) is deliberately **not** preserved, because it created a consistency window in which a `JournalEntry` was posted while the `AccountingDocument` remained DRAFT. This is an intentional improvement over legacy behaviour, not a compatibility regression. Callers must no longer mark the document posted themselves. (Resolves Q-0003.)
- 2026-09-19 — `AdvisorAccessGrant.revoke()`'s parameter is `revoked_by`, matching the field it sets and the BR-PRACTICE-002 acceptance contract. The legacy tree had the acceptance test calling `revoked_by=` against a model declaring `revoked_by_user=`, so that test could never have passed anywhere. One keyword was updated in `tests/identity/unit/test_models.py`; the assertions were left untouched. `ApiToken.revoke()` still takes `revoked_by_user` — tracked as F-0006. **Re-confirmed this session: kept as-is, both call sites green.**

There is **no bypass of any kind** and there must never be one.
